# Notepad3 C-to-C++ migration plan

## Goal and scope

Migrate all first-party main `src` C translation units, including style-lexer definitions and string/path libraries, to C++20 `.cpp`/`.h` translation units. This does not mean C++20 `import`/`export` modules. Rename each first-party `.c` file as it is converted and keep every stage buildable. First establish C++ compilation and compatible behavior, then modernize and retire DynStrg.

Remove C-only shims when no remaining consumer needs them, but retain typed, ABI, or behavior-bearing adapters when justified. Preserve behavior by default; obtain individual approval for behavior or support changes, except the already-approved DynStrg null/empty simplification below. Keep the main solution and its dependent consumers working. The alternate `other_sln\Notepad3DLL` project is outside the migration scope; report its baseline and impact without repairing it. The completion gate is the existing Release CI matrix plus representative Debug builds.

### String selection and portability decision gate

- **Measure, do not assume.** Map existing mutable-buffer, null/empty, aliasing, length/capacity, failure and Win32 output-buffer usage before adapting callers. The user approved eliminating DynStrg's null-versus-empty text distinction: treat an uninitialized text buffer as empty in the replacement, update callers and tests accordingly, and do not require candidates to reproduce that distinction. Keep invalid objects and allocation failures distinguishable from successful empty values where needed. Compare the existing DynStrg implementation, a `std::wstring` baseline, and feasible candidates on representative real application/path operations; expected results may differ for the approved null/empty simplification. Prefer a small native mutable UTF-16 RAII candidate for evaluation, without committing to its implementation or assuming it is smaller. Evaluate Scintilla/Lexilla's existing interfaces rather than copying internal code: current Scintilla Win32 code uses `std::wstring` and `std::wstring_view` (`scintilla\win32\ScintillaWin.cxx:1224`); `TextWide` is an internal conversion buffer (`scintilla\win32\PlatWin.h:150-165`), not an established general-purpose replacement. Review any reuse and licensing before adoption.
- Evaluate `winrt::hstring` and WIL's `wil::unique_hstring` as **alternative** owners of WinRT `HSTRING`, not nested owners of the same handle. `winrt::hstring` already manages ownership; WIL manages an ABI handle. HSTRING is immutable and its null handle denotes an empty string, consistent with the approved simplification; DynStrg currently permits a valid handle with no text buffer, so affected callers still need adaptation. WinRT has a separate mutable construction buffer followed by promotion; this is not a general in-place mutation API. Address mutable-buffer use and failure behavior with an explicitly designed representation or reject the candidate. See [HSTRING](https://learn.microsoft.com/en-us/windows/win32/winrt/hstring) and [WindowsPreallocateStringBuffer](https://learn.microsoft.com/en-us/windows/win32/api/winstring/nf-winstring-windowspreallocatestringbuffer).
- Treat ATL/MFC `CStringW` as less preferred; distinguish ATL from MFC rather than assuming either necessarily adds the other's runtime. Evaluate it only if justified, including toolchain, licensing, static/dynamic linkage and portability costs. Do not introduce ATL, MFC, WIL, C++/WinRT packages or other dependencies without separate approval.
- Preserve the static CRT and portable deployment: no new redistributable runtime DLLs. Review any new Windows-supplied DLL or API-set import case by case before adoption; do not assume `RuntimeObject.lib` eliminates runtime dependencies (see [WindowsCreateString](https://learn.microsoft.com/en-us/windows/win32/api/winstring/nf-winstring-windowscreatestring)). Inspect direct and delay imports and account separately for dynamic/transitive loads. Preserve the supported Windows and architecture matrix unless separately approved.
- Compare fresh isolated linked Release Win32 and x64 applications under the same compiler, linker, flags, resource inputs and signing state, including executable bytes and section sizes, direct/delay import tables and deployment requirements. Record representative allocation/mutation costs and correctness, and distinguish temporary prototype overhead from the eventual removal of DynStrg. Expand to the other release targets and Debug gates before completion. An isolated microbenchmark or a header-only claim alone does not establish smaller final executables or fewer runtime dependencies. Choose a target only after reporting measurements and obtaining approval.

### Remaining modernization and validation

6. **Retire DynStrg and migrate paths incrementally.** Map each `HSTRINGW`/`HPATHL` field, ownership and mutation site, C consumers and buffer API. Apply the string selection and portability decision gate above before choosing an end-state; use `std::wstring` only as a comparison baseline for this replacement, and do not assume `std::filesystem` replicates Windows semantics. Migrate one end-to-end caller/domain at a time, keeping an explicit temporary bridge only while consumers remain. Eliminate the null-versus-empty text distinction as approved, adapt affected callers, and test the new behavior without conflating allocation failure or invalid objects with successful empty values. Preserve UTF-16 code-unit behavior, length/terminator/capacity semantics, invalidation and alias rules, Win32 output-buffer sizing and failure behavior; never write into reserved but unresized string storage. Rework allocations, global/struct initialization, copying and cleanup safely: nontrivial C++ objects cannot be treated as zeroed/memcpy-able C structs. Preserve PathLib's long-path, normalization, comparison, shell, file and directory semantics and error codes; do not replace them blindly with generic path operations. Explicitly test worker cancellation and shutdown before destroying referenced paths (`src\Helpers.cpp:580-658`), plus reentrancy, async ownership, synchronous notifications, INI/MRU round trips and `WM_COPYDATA` compatibility where changed. Define exception handling at Win32 callbacks, C ABI, thread entry points and allocation-failure boundaries; no exception may cross a foreign callback/ABI. Retire `HSTRINGW`, `Strg*`, `DynStrg` files and temporary bridge only when every first-party caller, PathLib, test and maintained consumer has moved and contract coverage passes.

7. **Finish modernization and cleanup.** Apply narrowly justified RAII for owned Win32 handles, buffers and undo scopes, and standard types where semantics are proven equivalent. Preserve ownership, destruction order, synchronous UI notifications, direct-call lifetimes, persistence, localization and file formats. Remove obsolete C linkage and migration scaffolding only after last consumer is gone; retain necessary integration adapters. Update actual conventions and relevant source-path references when changes invalidate guidance; don't reformat or reorganize unrelated code.

8. **Run completion gates and review.** For every phase record command, configuration, result and baseline comparison. Run relevant existing focused harnesses (encoding, open directory, create directory, lexer sorting, zoom tooltip and web templates) and new boundary tests when affected. Run actual linked Release solution builds for Win32, x64, x64_AVX2 and ARM64, and representative Debug Win32 and x64 builds, plus affected dependent-consumer builds. Verify solution mapping, the fresh linked application's target architecture/configuration and dependency provenance for each gate; merely finding an old executable or receiving a successful no-op MSBuild exit is insufficient. `Debug|ARM64` is not among the selected gates and must not be reported as a successful application build without a separate mapping fix/approval. Verify runtime behavior with a safe, approved desktop/GUI smoke and a documented manual matrix where automation is insufficient; report unrun cases and cross-architecture execution limits. A `ClCompile` success is compiler feedback, not integration. Run the existing docs checker when docs change. Review diffs, source/project membership, residual DynStrg references, filename-based tests/CI filters, warnings, behavior changes and vendored patch preservation. No stage is accepted with unresolved regressions; distinguish existing failures from new ones.

## Decision gates and risks

- Obtain individual approval before changing platform/toolset support, adding dependencies, changing exception policy or exported ABI, editing vendored libraries, or expanding alternate-project scope. Report existing alternate-project problems and migration impact rather than silently fixing unrelated issues.
- Preserve existing user work and use only read-only Git operations unless explicitly authorized. Do not clean outputs or use desktop automation on the shared machine without approval; ask before dependency restore, installation, CI dispatch or other commands outside repository guidance.
- The approved `/EHs` policy does not guarantee C++ object destruction for structured exceptions; explicit SEH cleanup and callback boundaries still require attention. Validate ARM64 behavior and consider allocation failure, exceptions and partially completed operations for every string candidate rather than assuming DynStrg-equivalent failure semantics.
- Sibling Notepad4 is reference material only; compare patterns, interfaces and licensing before any reuse. Do not transplant its assumptions or Scintilla version.
- Treat this program as multiple independently reviewable stages, not permission to proceed past future stop conditions.
