# Notepad3 C-to-C++ migration plan

## Goal and scope

Migrate all first-party main `src` C translation units, including style-lexer definitions and string/path libraries, to C++20 `.cpp`/`.h` translation units. Also migrate first-party companion C consumers where needed to retire broad internal C-linkage blocks. This does not mean C++20 `import`/`export` modules. Rename each first-party `.c` file as it is converted and keep every stage buildable. First establish C++ compilation and compatible behavior, then modernize and retire DynStrg.

Remove C-only shims when no remaining consumer needs them, but retain typed, ABI, or behavior-bearing adapters when justified. Preserve behavior by default; obtain individual approval for behavior or support changes, except the already-approved DynStrg null/empty simplification below. Keep the main solution and its dependent consumers working. The alternate `other_sln\Notepad3DLL` project is outside the migration scope; report its baseline and impact without repairing it. The completion gate is the existing Release CI matrix plus representative Debug builds.

### String migration and portability safeguards

- **Preserve contracts, do not assume equivalence.** Map existing mutable-buffer, null/empty, aliasing, length/capacity, failure and Win32 output-buffer usage for each affected batch. The user approved eliminating DynStrg's null-versus-empty text distinction: treat an uninitialized text buffer as empty in the replacement, update callers and tests accordingly, and do not conflate invalid objects or allocation failures with successful empty values. Test representative changed operations against existing behavior, allowing for the approved null/empty simplification. If a material incompatibility or unacceptable cost arises, report it before changing the selected target. Scintilla's `TextWide` is an internal conversion buffer (`scintilla\win32\PlatWin.h:150-165`), not an established general-purpose replacement; review reuse and licensing before adopting any other implementation.
- If an alternative is needed, evaluate `winrt::hstring` and WIL's `wil::unique_hstring` as **alternative** owners of WinRT `HSTRING`, not nested owners of the same handle. `winrt::hstring` already manages ownership; WIL manages an ABI handle. HSTRING is immutable and its null handle denotes an empty string, consistent with the approved simplification; DynStrg currently permits a valid handle with no text buffer, so affected callers still need adaptation. WinRT has a separate mutable construction buffer followed by promotion; this is not a general in-place mutation API. Address mutable-buffer use and failure behavior with an explicitly designed representation or reject the candidate. See [HSTRING](https://learn.microsoft.com/en-us/windows/win32/winrt/hstring) and [WindowsPreallocateStringBuffer](https://learn.microsoft.com/en-us/windows/win32/api/winstring/nf-winstring-windowspreallocatestringbuffer).
- Treat ATL/MFC `CStringW` as less preferred; distinguish ATL from MFC rather than assuming either necessarily adds the other's runtime. Evaluate it only if justified, including toolchain, licensing, static/dynamic linkage and portability costs. Do not introduce ATL, MFC, WIL, C++/WinRT packages or other dependencies without separate approval.
- Preserve the static CRT and portable deployment: no new redistributable runtime DLLs. Review any new Windows-supplied DLL or API-set import case by case before adoption; do not assume `RuntimeObject.lib` eliminates runtime dependencies (see [WindowsCreateString](https://learn.microsoft.com/en-us/windows/win32/api/winstring/nf-winstring-windowscreatestring)). Inspect direct and delay imports and account separately for dynamic/transitive loads. Preserve the supported Windows and architecture matrix unless separately approved.
- For meaningful migration checkpoints, compare fresh isolated linked Release Win32 and x64 applications under the same compiler, linker, flags, resource inputs and signing state, including executable bytes and section sizes, direct/delay import tables and deployment requirements. Record relevant allocation/mutation costs and correctness, and distinguish temporary bridge overhead from the eventual removal of DynStrg. Do not repeat a standalone selection benchmark before each batch. Expand to the other release targets and Debug gates before completion; a pilot does not establish smaller final executables or fewer runtime dependencies.

### Remaining modernization and validation

6. **Retire DynStrg and migrate paths incrementally.** Map each `HSTRINGW`/`HPATHL` field, ownership and mutation site, C consumers and buffer API. Use `std::wstring` for owned UTF-16 text and paths; retain PathLib's Windows-specific operations rather than assuming `std::filesystem` has equivalent semantics. Migrate one end-to-end caller/domain at a time, keeping an explicit temporary bridge only while consumers remain. Eliminate the null-versus-empty text distinction as approved, adapt affected callers, and test the new behavior without conflating allocation failure or invalid objects with successful empty values.

   For each writable Win32 call, check its exact units, terminator and error contract: resize actual writable string storage before passing `data()`, reconcile the returned length after success, and handle insufficient buffers and failures without publishing partial or invalid data. Do not write into reserved but unresized storage or assume `capacity()` is the current writable length. Preserve UTF-16 code-unit, terminator, capacity, embedded-NUL, pointer invalidation and alias rules; use explicit Windows UTF-8 conversion for narrow text. Review overlapping inputs and pointers retained across mutations. Characterize existing differences such as `StrgDelete`'s return value and each caller's failure handling rather than treating method names as equivalent.

   Look for measured opportunities to use `std::wstring_view` or `std::string_view` for read-only, length-aware operations instead of making temporary copies, without changing text encoding or semantics. Views do not own storage: ensure the owner outlives each use, and never retain a view across owner mutation, reallocation, destruction or asynchronous work unless its lifetime is independently guaranteed. A view is not necessarily NUL-terminated; use an appropriately terminated owner or buffer for Win32 and other APIs that require one. Preserve owned copies for watcher and icon jobs that can outlive their callers. Add focused tests for affected substring boundaries, aliasing and lifetime-sensitive paths, and measure allocation or performance benefits rather than assuming them.

   Define allocation-failure translation and exception containment at Win32 callbacks, C ABI and thread entry points; no exception may cross a foreign callback/ABI. Rework allocations, global/struct initialization, copying and cleanup safely: nontrivial C++ objects cannot be treated as zeroed/memcpy-able C structs. In particular, `FileWatchRun` is currently allocated with `GlobalAlloc` (`src\Notepad3.cpp:14338`); any value-owned string members require real construction and destruction while preserving asynchronous reference-counted retirement. Preserve PathLib's long-path, normalization, comparison, shell, file and directory semantics and error codes. Explicitly test cancellation, reentry and shutdown while icon and watcher jobs retain their own paths (`src\Dlapi.cpp`, `src\Notepad3.cpp`); do not assume UI cancellation joins them. Also test synchronous notifications, INI/MRU round trips and `WM_COPYDATA` compatibility where changed. Retire `HSTRINGW`, `Strg*`, `DynStrg` files and temporary bridge only when every first-party caller, PathLib, test and maintained consumer has moved and contract coverage passes.

7. **Migrate internal C consumers and remove broad linkage blocks.** With the string target selected, inventory each broad `extern "C"` block and its declarations, definitions, callers, callbacks, exports, companion projects and test harnesses. Distinguish C++-only internal symbols from actual C, external-library and ABI boundaries; account for transitive includes and declarations inheriting linkage. Convert first-party companion C consumers as needed, starting with MiniPath's shared DarkMode dependency and its remaining C translation units. Rename and update project, filter, script, CI and test references in dependency-aware batches; preserve behavior, calling conventions and each intermediate mixed-language build. Keep shared or vendored C libraries unchanged unless separately approved; where they still call application code, retain or introduce a narrow C-compatible boundary instead of converting them blindly.

   Once each internal interface has no remaining C consumer or required external ABI, change its declarations, definitions and C++ callers together to ordinary C++ linkage and remove or narrow the surrounding blocks, including the style-lexer definitions and registry where eligible. Do not remove a block from one side in isolation. Keep existing C-caller coverage for real C boundaries; adapt migration-only C harnesses to C++ without losing behavioral cases, and retain mixed-language and x86 calling-convention tests where interop remains. Preserve Lexilla `CreateLexer`, other real C APIs and required exported symbols; C linkage alone neither exports a symbol nor guarantees full ABI compatibility. Avoid wrapping C++ templates or headers in C linkage and preserve callback signatures, ownership, exception boundaries and object/layout semantics. Compare Notepad4's approach, not its code or assumptions.

   For each batch, run focused regression and mixed-link checks for affected interfaces and actual isolated linked builds of Notepad3, MiniPath and any other affected maintained consumers on Win32 and x64; distinguish compiler-only feedback from linking. Extend to the remaining completion configurations and approved runtime checks under stage 9. Stop for approval before altering an external/exported ABI, vendored code, support policy or the out-of-scope alternate project. If a necessary C consumer cannot be migrated safely, retain a narrow adapter and document the reason and remaining coverage.

## Decision gates and risks

- Obtain individual approval before changing platform/toolset support, adding dependencies, changing exception policy or exported ABI, editing vendored libraries, or expanding alternate-project scope. Report existing alternate-project problems and migration impact rather than silently fixing unrelated issues.
- Preserve existing user work and use only read-only Git operations unless explicitly authorized. Do not clean outputs or use desktop automation on the shared machine without approval; ask before dependency restore, installation, CI dispatch or other commands outside repository guidance.
- The approved `/EHs` policy does not guarantee C++ object destruction for structured exceptions; explicit SEH cleanup and callback boundaries still require attention. Validate ARM64 behavior and consider allocation failure, exceptions and partially completed operations for every string candidate rather than assuming DynStrg-equivalent failure semantics.
- Sibling Notepad4 is reference material only; compare patterns, interfaces and licensing before any reuse. Do not transplant its assumptions or Scintilla version.
- Treat this program as multiple independently reviewable stages, not permission to proceed past future stop conditions.
